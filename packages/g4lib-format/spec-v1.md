# .g4lib — Game4 Community Catalog, version 1

A portable UTF-8 JSON snapshot of historical metadata, content relationships, declared integrity identities, distribution references and authorized artwork. The media type is `application/vnd.game4.catalog+json`. It is not .g4 payload storage, an executable, an account, a subscription, or proof of authorization/availability. No mandatory encryption, DRM or central service is used.

The root has exactly `format: "game4-community-catalog"`, `schemaVersion: 1`, `id`, `name`, `attribution` and `data`. All properties are required; unknown fields are rejected in v1. `v1.schema.json` supplies structural validation; consumers MUST also enforce the semantic rules below. `synthetic.g4lib` is a clearly labeled metadata-only interoperability fixture with separate base/update/DLC records.

`data` contains arrays: `platforms`, `games`, `releases`, `editions`, `contents`, `dependencies`, `preservationFiles`, `p2pSources`, `assets`, `metadataSources`, plus empty `catalogs`, `catalogEntries`, `collections`, `collectionEntries` and `preferences` arrays. The latter are reserved for the shared private record model and MUST be empty in public v1 files. Property names use camelCase. UUIDs are recommended for publisher record IDs; readers also accept bounded ASCII alphanumeric identifiers with `-`, `_`, `:`. IDs are unique per entity and references must resolve within the document. IDs do not contain executable paths.

- Platforms contain name, manufacturer/family, nullable release year and history/description. Games own title, nullable year, developer, publisher, genre, description, development history and created/updated timestamps. A metadata-only game is valid.
- Releases link game/platform IDs and provide region, languages and titleId. Editions link releaseId and provide name/medium. Multiple platform releases are supported per game.
- Contents link editionId and have kind `version`, `update` or `dlc`, name, textual version/build/identifier, releaseDate, format, description and changelog. A `version` has null baseId. An update/DLC has a non-null baseId pointing to a `version` of the exact same edition. Dates are descriptive strings; compatibility is never inferred by comparing versions. Dependencies link contentId/requiredId within the same game and MUST be acyclic, including no self-dependency.
- Preservation files attach to contentId with name, format, canonical unsigned decimal sizeBytes, optional empty or 64-hex SHA-256 and null itemId/fileId. Names are metadata, never extraction/launch targets. No private absolute path or live machine identity is exported automatically.
- P2P sources have contentId, magnet, license, attribution and authorized boolean. Magnets must identify a single BitTorrent v1 info hash. Game4 normalizes references offline and does not follow advisory embedded URLs/peers. `authorized` is a publisher declaration; exporters/importers clear it and receiving users must review permission. Registered sources are not evidence of active seeders.
- Assets attach to exactly one platformId/gameId/contentId, with role `cover`, `banner`, `screenshot` or `console`, MIME `image/png`, `image/jpeg` or `image/webp`, byte array, source, license and attribution. There are no external image downloads or SVG/script assets. Pixels travel in the catalog and remain locally renderable offline. Rights/source declarations are mandatory, not independently certified.
- Metadata sources attach to gameId with source, attribution, note and createdAt. These are attribution/history, not cryptographic identity or signed revisions.

Game4 limits the encoded input to 32 MiB, artwork to 4 MiB each, a document to 500 platforms, 100,000 games and 100,000 content rows; detail reads are bounded. Unsupported versions, invalid relationships, duplicates, cyclic dependencies, noncanonical sizes, malformed hashes and private references are rejected before changing the live catalog. A successful import atomically namespaces all IDs by a SHA-256 digest of the parsed typed snapshot; identical imports are idempotent and differing snapshots remain separate. This digest is not a publisher signature. Consumers may use different non-destructive local identity mappings without changing public records.

Export uses exclusive file creation. Import is an explicit native-file selection followed by count/name/attribution review and confirmation; it never starts a transfer, enables DHT, subscribes to a server, runs a game, or overwrites a local record. Signature verification and live subscriptions require a future version/extension design; unsigned catalog contents must be treated as untrusted declarations.
