# G4EP — architecture and integration, step 1

Status: step 1 architecture baseline, November 14, 2026. At that checkpoint no codec/runtime was installed. **Step 2 now implements the offline streaming encoder and local verification utility; see [encoding and validation](encoding.md).** A decoder application, storage server, fragment transport, private authentication and repair worker remain later work. No G4EP IPC command, UI button, migration, socket or automatic startup hook is registered. The multi-computer acceptance transfer remains a later gate.

G4EP (Game4∞ Eternal Preservation Protocol) preserves arbitrary bytes. ISO, ROM, ZIP, video and other input types follow the same pipeline. Original files remain read-only; packaging in .g4 and importing into the historical catalog are optional. The protocol name expresses intent, not a guarantee of eternal availability.

## Isolated module and ports

`apps/desktop/src-tauri/src/g4ep/` contains `types.rs`, `ports.rs` and contract tests, exported through `lib.rs`. It depends only on dependencies already present. It does not import the Library, Tauri window, SQLite or torrent runtime. Blocking file/codec work and asynchronous network streams have separate interfaces. Adapters and an application service compose these ports later; there is no success-returning dummy implementation.

| Port                    | Responsibility and success condition                                                                                                                                                                                                                                                                                    |
| ----------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `Encoder`               | Stream exactly the declared source length, compute whole-object SHA-256, encode one stripe at a time, emit padded immutable shard descriptors through `FragmentSink`, return complete structurally valid metadata only after success. Exposes a codec registration identity.                                            |
| `Decoder`               | Select the matching codec, obtain at least k distinct SHA-256-verified shard indexes per stripe through `FragmentSource`, reconstruct ordered original bytes, trim only final padding and validate original size/hash before success. Writes to staging; the caller publishes atomically without overwriting originals. |
| `StorageNode`           | Host-owned, quota-reserved content-addressed storage; temporary writes, exact size/hash verification, synced atomic no-clobber commit, bounded requested inventory and capacity. Reads are reverified by consumers. No arbitrary filesystem listing or remote-delete method exists.                                     |
| `PeerDiscovery`         | Discover enrolled private peers only. Return bounded allowlisted node/address pairs. Discovery is not authentication or evidence of custody.                                                                                                                                                                            |
| `FragmentTransfer`      | Async upload/download to explicitly enrolled peers, authentication/rate/time/size limits, local integrity verification and temporary sinks. BitTorrent receipts or remote acknowledgements alone do not prove long-term storage.                                                                                        |
| `IntegrityVerification` | Bounded streaming SHA-256 and exact length for a fragment or whole object. Local verification report is separate from node observations and publisher authenticity.                                                                                                                                                     |
| `RepairManager`         | Assess fresh observations by stripe, coordinate and failure domain, generate an expiring plan, revalidate before execution and verify every reconstructed/copied fragment before placement. Report unrecoverable stripes honestly.                                                                                      |

All long work receives `OperationContext` with a cancellation token and deadline; implementers must check it within loops and I/O boundaries, not just on entry. Network methods return object-safe `Send` futures and use async readers/writers. Codec/local storage methods are blocking and must run on a worker (for Tauri, `spawn_blocking`). Never hold catalog SQLite locks during codec execution, a peer wait or a native picker.

## Data and integrity model

- **Object**: original byte length plus whole-file SHA-256. The same bytes have the same object identity across filename/extension/catalog entries. A hash is not a license or signature.
- **Coding profile**: k data shards, m parity shards, fixed encoded shard byte length and a separate codec registration key. `CodecId` dispatches the encoder/decoder; field polynomial, matrix construction, index ordering, padding and compatibility vectors must be fixed before an actual codec ID/wire version is published. Reed–Solomon over GF(256) is the proposed first codec, not an implemented dependency.
- **Stripe**: ordered original data span of k × shardBytes; the final span is zero-padded to the same length. The decoder emits exactly originalLength bytes, then verifies the whole-file hash.
- **Fragment**: stripe number, distinct shard index, full encoded length and SHA-256. Hash checks cover encoded parity/data bytes including padding. Storage uses digest-derived names, never an untrusted input filename.
- **Manifest**: complete mapping of original identity, codec/profile and all fragment descriptors. `ValidatedManifest` validates geometry, coordinate uniqueness/ranges, declared lengths and bounds only. It does not read source/shards, certify the codec, authenticate metadata or establish preservation.
- **Observation**: node, fragment, health and observation time. Multiple claims for one shard index do not become multiple reconstructible shards. Duplicate content at one host does not become an independent failure domain.
- **Repair plan**: binds the validated manifest, exact actions/targets and expiry. A repair service must check that all coordinates/descriptors belong to the manifest, peer enrollment, quotas, freshness, current availability and cancellation again before I/O. Planning types do not enforce a plan executor by themselves.

Planning constructors bound k ≥ 2, m ≥ 1, k+m ≤ 255, shardBytes between 64 KiB and 4 MiB, total stripe shard bytes ≤ 64 MiB, source bytes ≤ 1 TiB and at most 1,000,000 fragment records. These are internal resource guards, not an advertised support/benchmark envelope. A profile can reach the fragment-record bound before the source-byte bound. Final source/path/metadata/transport/codec limits need enforcement in the corresponding adapters.

## Approximately 700 MB experiment

Proposed first profile: **8 data + 4 parity shards, 1 MiB per shard**. This gives an 8 MiB data stripe and 12 MiB of shard buffers, excluding codec work memory, metadata and transport queues. Begin with one active stripe and bounded transfers; measure total process memory rather than claiming a hard 12 MiB process footprint.

| Input size                  | Stripes | Encoded fragments | Encoded bytes including final padding |
| --------------------------- | ------- | ----------------- | ------------------------------------- |
| 700,000,000 bytes (700 MB)  | 84      | 1,008             | 1,056,964,608                         |
| 734,003,200 bytes (700 MiB) | 88      | 1,056             | 1,107,296,256                         |

The 700 MiB case has 4 MiB of final data padding. Shard count/size arithmetic is tested without allocating or reading a 700 MB file. Encoding requires additional local disk capacity (~encoded size plus source and any simultaneous reconstruction); calculate quota and free-space reservations before accepting a future job.

For a correct MDS codec, any k distinct valid shards can reconstruct a stripe; losing more than m shards in **one stripe** can defeat reconstruction even when most other stripes are healthy. Four parity shards do not automatically mean tolerance of four failed computers. With 8+4, two hosts holding six shards each cannot survive either host's total loss. Three hosts with four different shards per stripe each can in principle survive one host loss, subject to actual placement/verification. A two-PC first experiment can validate authorized transfer and controlled shard loss, not claim independent-host disaster tolerance.

## Private networking boundary

The first runtime must use explicit enrollment and private bind addresses, e.g. LAN or a private overlay such as Tailscale. `PrivateNetwork` accepts loopback, RFC1918 IPv4, IPv4 link-local, IPv6 ULA/link-local and CGNAT 100.64/10 overlay addresses, requires nonzero ports, bounds peers to 32, rejects duplicate identities/endpoints and denies non-enrolled node/address pairs. This classification does not prove a secure route, permission or peer identity; bind/firewall/overlay ACLs and pinned peer authentication must also be enforced by the future adapter.

**No default public DHT bootstrap, trackers, PEX, UPnP, multicast/broadcast discovery or public announcement is permitted in the initial G4EP adapter.** The existing torrent engine defaults/policy are separate: its discovery controls and PEX do not implement this isolation automatically. Do not pass G4EP traffic to the current manager and assume `dht=false` makes it a private transport. Choose/validate a dedicated fragment session/transport adapter before multi-machine acceptance. No new custom transport is implemented in step 1.

BEP 5 DHT maps torrent info hashes to peer contact information; it is not an erasure-code object registry or an authenticated fragment inventory. Public DHT compatibility can be investigated later behind a separate adapter/explicit opt-in, without exposing private endpoint identities or local paths. Initial discovery should work with a provided peer list even if every official Game4 server is absent.

No account, wallet, mandatory encryption format, DRM or central dependency is introduced. Transport authentication and protection are still required for private operation; choosing them is not equivalent to encrypting original preservation packages. Do not hand-roll authentication or treat an IP, NodeId or SHA-256 alone as proof of a trusted peer.

## Persistence and format compatibility

Proposed future private root: `g4ep/` under the existing app-local data directory, containing `state.sqlite3`, owned shard storage, staging and reconstruction directories. A future private schema should separate objects, codec/profile versions, stripes, fragment identities, local locations, enrolled nodes, observed remote copies, jobs/checkpoints, reservations and repair attempts. Persist quota reservations/idempotent jobs and local copy health, not unsanitized remote paths. Restart paused with no network or automatic repair until the user explicitly enables a private session. Plan garbage collection separately from repair; never delete a last known copy as a repair shortcut.

There is **no migration/store constructor now**, so existing catalog schema 5, backup v3 and transfer SQLite v1 are unchanged. A separate store needs explicit future backup/recovery semantics; do not imply current Library backups include future shard payloads.

`.g4`, `.g4e` and `.g4lib` keep their current versions and validators. A G4EP recovery descriptor will need a separately specified/versioned envelope, exact codec parameters, canonical hash/signature policy, resource limits and compatibility vectors before public serialization. The Rust model deliberately derives neither Serde nor TypeScript wire exports. No new extension is associated with Windows. In particular, .g4e v1 `extensions` are advisory and cannot silently become mandatory recovery instructions. A future optional reference must remain explicitly reviewed and must not trigger network I/O while parsing.

## Integration sequence and next acceptance gates

1. **Completed here**: inspection, isolated ports, bounded planning types, private enrollment constraints, architecture/decision and contract tests.
2. Fix the codec algorithm/library/license and deterministic test vectors; implement streaming encode/decode with odd lengths, empty input, corruption, k−1/k shard boundaries, cancellation and source changes. Freeze a descriptor only after compatibility tests.
3. Implement owned shard storage and versioned private persistence: quotas, no symlinks/junctions, disk-full/locked-file handling, atomic commits, recovery and re-verification.
4. Implement/authenticate explicit private peers and bounded transfers with no public discovery or collateral announcements. Validate adapter traffic before using real machines.
5. Add bounded observations/repair and the real Tauri commands, generated TS DTOs, progress/errors and reused React controls, with no inactive success buttons.
6. Run the authorized ~700 MB acceptance: original SHA-256, encode, distribute to two real computers, verify every received fragment, lose controlled indexes within m per stripe, reconstruct to a **new** file, compare SHA-256/length, restart/resume, corrupt a fragment, exceed recovery limits and test repair under explicit session consent. Record actual bytes, time, memory, disk, topology, routing/relay and failure domains.

The owner has supplied steps 1 and 2 of their ten-step plan; this sequence describes dependencies, not invented instructions for the remaining nine steps. A later scheduled repair can be automatic **inside an explicitly enabled session**, with quotas/rates and cancellation; opening the app or importing metadata must not silently enroll the device.
